# R7.5.A — Durability, Receipt and Failure Baseline

This document records observed current behavior to support R7.5 owner decisions. It does not approve new persistence, retry, replay, deduplication, schema, or ACK behavior. “Write completed” below means the current API call resolved; it does not mean `fsync`, power-loss durability, downstream storage, or exactly-once execution.

## Failure windows and evidence boundaries

| Event | Current consequence established by source/tests | Evidence status / limit |
|---|---|---|
| Validation or receipt I/O rejects before file write completion | F08/F09/M13 return their existing `INVALID_MESSAGE` or `DELIVERY_FAILED`; no receipt notification/deferred work after caught save failure. | Tested with controlled/faulting stores; does not prove a failed write left no file. |
| Process dies after receipt write but before/around ACK | File may exist while sender did not observe ACK; retry is not an idempotent replay (F08/F09 exclusive ID may reject; M13 makes a new random receipt). | Source-derived window; abrupt process termination not simulated. |
| Process dies after ACK before deferred work completes | In-memory `setImmediate` callback is lost. Receipt/result/history data can remain, but startup does not enqueue it. | Source-derived; no crash/restart replay test. |
| Process dies during direct JSON write | `writeFile` targets final path directly; partial/truncated JSON is possible. No atomic temp/rename or cleanup protocol is present. | Risk inferred from write method; no partial-write/crash test. |
| OS crash or power loss after write resolution | No explicit file `fsync`/directory sync is called. SQLite uses WAL but this code does not set a synchronous policy. | **Unverified**; no power-loss claim or test. |
| Graceful application stop | M02 closes PServer/socket/HTTP resources and persistence but does not drain M12/M13 scheduled work. A scheduled closure may still be pending or encounter closed dependencies. | Source-derived boundary; coordinated bounded drain belongs to R7.6 (TD14). |
| Remote disconnect/rejection after receipt | M12 records later `forwardFailed`; M13 tries status sidecar and independent notification. A downstream `{ok:true}` is a peer protocol acknowledgment, not proof of durable business completion. | Unit and loopback tests cover local semantics; external peer interpretation unverified. |
| Duplicate sender retry | F08/F09 are exclusive-create and reject repeated IDs; M13 does not key on peer message ID and creates a second receipt. M09 has no durable dedupe. | Tested for F08/F09 and M13; policy remains undecided. |
| M13 sidecar update fails after send attempt | Existing workflow still publishes the result derived from send attempt; history may show `pending` when sidecar is absent, or read may fail on malformed sidecar. | Tested for store rejection and unknown status; malformed sidecar JSON is source-derived, not crash-tested. |

“Forwarded” for peer workflows means current M10 delivery resolved according to its peer ACK handling. It is not a claim of exactly-once business execution. M09's generic socket broadcast has weaker acknowledgment semantics than peer `peer:message` delivery.
