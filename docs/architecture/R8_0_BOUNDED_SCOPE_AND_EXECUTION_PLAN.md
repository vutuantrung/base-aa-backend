## Sequencing proposal

**Risk-first order is recommended over automatic numbered order, but no next checkpoint is approved.** The rationale is evidence readiness, not phase-number preference:

1. Owner first names any available provider/target boundaries. Without them R8.2 and R8.4 stop without inferring absence.
2. If approved, R8.3.A can independently bound what existing process-crash tests prove, because its local evidence already exists and does not depend on a deployment provider. It must not imply new failure-injection execution.
3. R8.1.A is a separate low-risk docs-only conformance inventory; run only if the Architecture Owner identifies a decision to be informed by it. Existing checker pass is not itself a reason for refactoring.
4. R8.2 and R8.4 can proceed only for specifically named channels/targets, and may be parallelized only if their evidence owners and safe boundaries are distinct and available.
5. R8.5 follows only accepted outputs that actually ran. An unstarted or blocked checkpoint remains visible as such.

Original numbering order is also possible, but would leave high-impact TD18/19 and R7.5 external proof unaddressed while it performs low-value static review first. Conversely, starting external checks first is impossible without SC-D02's provider/target prerequisite. The owner can select a different order with explicit rationale.

## Verification and stop policy

- For planning/docs-only work: Node.js `v22.23.5` / npm `10.9.9`; architecture check, test-manifest check, diff checks, new Markdown whitespace/link checks. No Full, serial backend, Fast, Integration, playground, typecheck or build is required for R8.0.
- A separately authorized test/code checkpoint must name changed contracts and files, run focused tests and typecheck/build where relevant, then preserve the 55-entry manifest, Fast/Integration/Full profiles, maintained serial backend and separate playground. Capture complete logs, environment/metadata and failure identity; cap attempts per owner scope.
- External claims require the named operator/maintainer/product/receiver evidence; mocks, loopback and local process termination remain qualified by their environment.
- Each checkpoint exits with evidence, residual unknowns, file inventory, owner decision state and bounded rollback. Any missing owner/target, unsafe data boundary, unexplained behavior, or need for a new production seam means stop and document.
- Approval of this roadmap grants no implementation. Every execution checkpoint requires separate bounded Architecture Owner approval.
