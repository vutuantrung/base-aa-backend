## Factory and repository typing

- `createApplication` overloads are synchronous (`create-app.ts:38-41`): omitted/`true` SQLite config returns concrete non-optional session/usage/catalog handles; literal `false` returns `ApplicationInstance` with repository properties typed `T | undefined`; a general boolean config uses the broad overload and also returns optional handles.
- Runtime construction follows `enableSqlite ?? true`; `openPersistence` creates DB or returns `undefined` (`persistence.ts:5-14`). Enabled opening can throw if `better-sqlite3` is unavailable (`sqlite.ts:6-12`). When DB is absent, all three repository fields are actually `undefined` (`create-app.ts:44,51-53`).
- `resolveConfiguration` always supplies a boolean; its standalone default is false, so `startApplication(configuration)` resolves to the broad `ApplicationInstance` signature (`lifecycle.ts:7-12`) even though programmatic omission selects the enabled overload.
- `stopApplication` deliberately requires only a close capability (`Pick<..., 'close'>`). `MessageSender`, Session/ProcessUsage/AaCatalog repository interfaces already exist for M05/M07 injection; only session/usage behavior currently uses the corresponding app handle in tests. Catalog app writers remain concrete public integration methods used by tests/docs.
- Late-bound `router` at `create-app.ts:47-62` resolves construction ordering: the sender closure is created before the router is assigned, and listeners/start occur after assignment. This audit recommends no redesign.

## Bounded D.2 recommendation and approval boundary

1. **Retain the current surface** (recommended baseline): preserve all 11 names, concrete types, overloads, optionality, constructors and runtime identities. This has no tracked breakage and avoids treating absence of external use as proof.
2. **Add consumer-driven capability views alongside the legacy API** only if an identified consumer needs one. Existing candidates are `MessageSender`, `SessionRepository`, `ProcessUsageRepository`, the read-only `AaCatalogRepository`, and the close-only lifecycle pick. Transform registration and catalog writes demonstrate why some current concrete handles are not replaceable by those narrower ports.
3. **Narrow/remove a legacy property or overload** only after explicit compatibility approval and a consumer inventory for the target deployment/package boundary. No writer port should be invented just to make tests appear neutral.

If D.2 is authorized, acceptance should type-check omitted/true/false/dynamic SQLite calls and `startApplication`; cover actual repositories present/absent, per-instance isolation, all existing catalog upserts and reader methods, `enableTestPeers`/PServer connector absent and present combinations, HTTP listen/close, and `stopApplication` with close-only input. Preserve late-bound routing and existing API semantics.

Explicit user decisions needed before any narrowing: whether `ApplicationInstance` is a supported external API; whether legacy fields/types/overloads may change; whether additive capability views are wanted and which consumer owns them; whether catalog writer methods are intended public API or internal integration surface. No decision is made here. M12–M15 APP/DEMO TBD, bounded shutdown drain, HTTP semantics, gateway composition, M10/M11 and dependency enforcement remain outside D.1/D.2 scope.
