## 2. Approved D01–D06 (normative)

### D01 — M02 single one-shot lifecycle owner

M02 owns coordination; modules own their resources/business logic. Keep existing public `ApplicationInstance` shape and `listen(port: number): Promise<number>`, `close(): Promise<void>`; no new public lifecycle methods. The specifically approved additive configuration is total shutdown timeout; choose an intent-revealing optional internal/application config field consistent with existing config conventions, document units/default/validation and thread it through runtime config if applicable. No unrelated API redesign.

Use explicit internal states created, starting, running, draining, stopping, stopped, failed (terminal unsuccessful startup or shutdown). Local readiness separate. Same requested port concurrent listen calls share outcome (including port 0); same requested port after running returns actual bound port. Different port rejects without disrupting active start/running. Concurrent/repeated close shares terminal outcome, including rejection; close before listen releases acquired resources. Close during start fences late startup completions, rejects interrupted listen, prevents a subsequent ready state or PServer connect, and cleans acquisitions safely. No restart of an instance; listen after closing/closed/failed rejects. Promise identity is not the contract, shared result and exactly-once acquisition/cleanup are. Establish synchronous admission/lifecycle linearization points before asynchronous work. Preserve startup root cause, attach cleanup failures. Avoid cyclic waits between startup rollback and concurrent close.

### D02 — Internal readiness and explicit admission

Local ready only after required local initialization/recovery and listener serving; false at cutoff, failure and stop. Optional disabled components do not imply not-ready; PServer session readiness, per-target availability and capacity independent. No /ready endpoint, no /health change; keep `{status:"ok"}` when existing route responds. Do not require remote connection for local startup success.

One app-owned admission decision with narrow injected capabilities, covering HTTP applicable operations, existing and new Socket.IO connections/events, M04 ingress, direct exposed sender/router entry points, and owned snapshots. Inventory exact route/event surfaces and existing precedence before editing. Preserve R7.3 auth-first and optional SQLite capability matrix including exact paths, unknown routes and route-specific validation/status behavior. Apply HTTP 503 only to otherwise applicable business operations during drain; use existing error body convention with stable draining reason; document exact response and test. Do not turn unmounted/disabled routes or unauthorized requests into drain errors. Keep health readable while listener exists. Do not add new public ACK codes; ACK-bearing peer messages rejected at cutoff with existing DELIVERY_FAILED and stable draining reason. Preserve M04 pre-session-ready UNSUPPORTED_DESTINATION and logging precedence, and M04/M05 callback-gated peer messages (no callback => no processing, no synthetic ACK). Preserve generic socket ACK/no-ACK behavior and existing error format; reject new work using existing applicable failure shape, never invent success. Direct sender/router operation rejects internal lifecycle error. Do not retroactively reject already-admitted nested calls; propagate scoped admission ownership so one operation is not double-gated. No detached path may evade cutoff by holding an old connection. Avoid changing pre-listen direct-call semantics unless needed for safety and covered by approved readiness/admission policy; report any observable change and stop if unresolved.

### D03 — Drain already-admitted work only

At a synchronous cutoff: readiness false, admission closed, no new scheduler launches. Drain already admitted receipt preparation/commit/ACK and state projection, active sends and outcome commits, all active generic M09 fan-out branches, admitted HTTP/socket operations, and tracked snapshot reads or safely fence their notifications. Track through final dependency access and ACK/response emission, not merely through handler return or receipt acceptance. Nested operations inherit an admitted context, with cleanup in finally. Preserve public M09 Promise.all fail-fast semantics; independently track each started branch until settled (including siblings after aggregate rejection), keep branch errors handled, no new retries/rollback/aggregate response. For snapshots, keep current identity checks, fence late notifications and retain dependencies until reads settle. Do not own arbitrary M08 external clients.

Do not drain all durable queue records. Leave queued and future retryable work on disk; no new send/retry begins after cutoff. Cancel queued scheduler callbacks and process-wide limiter waiters logically; release slots exactly once. Define linearization of attempting write versus actual transport invocation: if cutoff races an in-flight pre-emit persistence step, fence before emit and settle safely as proven-unsent only if actually proven; otherwise uncertain/blocked, never infer unsent from timeout. Preserve attempt counts and retry eligibility. Already invoked sends may settle while transport and store remain usable; track final outcome persistence. No additional send from receipt commit completed during drain. Do not reinterpret a positive peer ACK as business completion.

Order: stop admission/new connection acceptance and scheduler launches while keeping established transport needed by admitted work; drain tracked operations; close PServer/peer/Socket.IO/HTTP according to actual dependencies; close stores and SQLite only when safe. Socket.IO may own HTTP close; avoid double-close/deadlock, verify actual version behavior. Do not await HTTP listener close in a way that blocks drain or disconnects peers needed by active ACKs. Prevent late startup/listen callbacks from opening resources after close. Never wait for a peer ACK after intentionally closing its transport as though it could still arrive.

### D04 — Single total monotonic shutdown deadline

Default 15,000 ms configurable, validate finite positive bounded values using documented units; no unrelated configuration changes. One absolute monotonic deadline captured at first close request, covers startup settlement, drain and dependency-safe cleanup. No reset per component or repeated close. Use injectable clock/deadline seam for deterministic tests; reserve cleanup time within budget if required, explain choice. Ensure timers cleared, rejections observed, late completions fenced. Promise.race is NOT cancellation. At timeout reject close with internal timeout error (Promise<void> preserved), retain root/cleanup diagnostics, do not mark safely stopped or falsely claim all resources released. Best-effort safe independent cleanup within remaining budget; do not close dependencies still used by unfinished operations solely to return success. Late acquisition must be fenced and disposed safely if it occurs, without starting new work or falsely releasing ownership. A hung synchronous call/event-loop stall cannot be preempted by JS deadline; record limitation. No process.exit in library. Preserve writer lock while any potential mutator exists, even on late callback, timeout or shared-store references. No automatic stale-lock removal. Supervisor/entrypoint handles actual termination.

### D05 — Dependency-safe aggregated cleanup and isolation

Register ownership as resources acquired, support partial synchronous construction and asynchronous startup rollback. Ensure failed construction after opening SQLite/creating sockets can clean acquired resources without changing createApplication's synchronous API; explicitly handle async disposal limitations, observe errors. Continue independent safe cleanup after one failure, aggregate errors, preserve startup primary cause. Idempotent disposal, no close of dependency used by active work. Retain per-instance isolation, process-wide 4-attempt cap, eliminate canceled waiters without slot leak or late sends. Same-directory ownership remains fail-closed across processes; verify same-process multiple app instances cannot simultaneously run duplicate delivery for same record (shared store references alone do not authorize competing runners). If exclusivity needs an additional policy, stop rather than silently broaden ownership. Different directories independent; no environment hacks in production. Preserve active/sticky lock evidence and verified-owner-dead operational procedure.

### D06 — Entrypoint signals and diagnostics

Signals owned only by main/entrypoint, never by application/library. Handle startup interruption as well as running shutdown; install handlers at a safe point before async startup, ensure cleanup/removal/test isolation, avoid creating ready app after signal. First SIGINT/SIGTERM starts same bounded close; normal success exit 0, startup/shutdown failure or timeout exit 1; second signal force-exits non-zero at entrypoint only. Use injectable exit/signal seam or child process tests, never kill test runner. Do not mask startup root cause. Minimal M18-compatible diagnostics (use existing facilities if present): phase, local readiness, counts of tracked work by class, deadline, cleanup result, lock preservation; no payloads, credentials, tokens or broad logging redesign. No new dependency on a nonexistent diagnostics module; document actual ownership.
