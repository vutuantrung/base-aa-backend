### R7.6-D02 — Readiness and admission
Compare internal readiness only, additive readiness endpoint, or altered health endpoint (not recommended without compatible contract). Propose local readiness independent of remote session/individual peers; distinguish degraded state and storage/admission failure, optional resources, startup/drain. Preserve /health, auth-first, disabled SQLite route matrix, ACK-gated ingress and existing public error codes. Specify gate for HTTP/Socket.IO/PServer/direct calls, grandfathered in-flight operations and exact rejection/ACK behavior including existing clients; no invented 503/ACK mapping without approval. Identify whether gate affects reads, health and existing connections differently.

### R7.6-D03 — Drain work set and ordering
Compare draining only already-started operations, bounded processing of additional eligible queued work, or immediate stop. Recommend stop new admission and new scheduler attempts; allow already accepted in-flight receipt commits and already-started delivery/outcome commits to settle while required transports/stores remain usable; leave queued/retryable future work durable for later recovery, no replay of uncertain/legacy. Define precise admission cutoff and ownership of pre-commit transformations, post-commit ACK, sync notifications, generic M09 sends, HTTP requests, snapshots and PServer session callbacks. Avoid a deadlock where transport waits for work which itself needs the transport. Provide a dependency-derived ordered shutdown sequence; do not close a dependency before known users quiesce. Do not silently introduce additional send attempts during drain.

### R7.6-D04 — Deadline, cancellation and timeout outcomes
Recommend a single monotonic total shutdown budget with configurable bounded default (propose e.g. 15 seconds, justify against existing 5-second peer ACK timeout plus persistence and transport close; not approved). Compare active drain and separate cleanup budgets within total deadline. Define what can actually be cancelled, logical fencing versus physical cancellation, timer/slot waiter release, late callback handling and process termination responsibilities. If an active operation cannot be stopped safely, preserve lock and evidence; never call an uncertain send unsent, never claim cancellation undoes remote actions, never release lock while a surviving writer could mutate state. Distinguish close() bounded return/rejection from actual process exit and from fully released resources. Explicit policy for timeout error/result shape, exit code/signals and supervisor escalation; no process.exit in library without approval. No automatic stale-lock removal.

### R7.6-D05 — Failure cleanup and ownership isolation
Compare fail-fast versus best-effort dependency-safe cleanup with aggregated errors. Recommend reverse acquisition/actual dependency ordering, continue independent safe cleanup, preserve root cause, record unreleased resources; idempotent close/partial initialization cleanup. Define store writer ownership and active-operation fencing, shared process limiter lifecycle, two app instances and same-directory contention. Keep P01–P06, fixed quotas and no data deletion. Do not reopen TD02 admission abort issue or add distributed locking/retention migration.

### R7.6-D06 — Runtime integration and diagnostics

Identify minimal structured lifecycle/readiness diagnostics and metrics (no broad observability redesign). Do not log payloads/secrets, change peer protocol or add public endpoints without consent.
